1. Cómo se evaluó

La matriz del 15 de septiembre describe un inventario del MVP local más el pase a Supabase. Desde entonces el producto avanzó: Auth real, sync, PDF, edición de perfil, filtros, aviso de borrador y aviso de conexión. Este informe actualiza cada ID contra el código de revestimientos-industriales y los documentos hermanos (alcance, checklist, propuesta de informe, README de Supabase).

  • Implementado: existe en la app y cumple el criterio de aceptación del alcance actual.
  • Parcial: hay una parte (p. ej. PDF sí, Excel no; Auth sí, vistas de supervisor no).
  • Fuera de entrega: roles, panel web y catálogos remotos, acordados para después.
  • No aplica en producción: reset de datos demo (RF-012), retirado del perfil.

6. Entidades, pantallas, catálogos y reglas

Modelo de datos

Las entidades de la matriz están cubiertas. El esquema real usa español (perfiles, clientes, proyectos, levantamientos, sectores, elementos, fotos) y campos extra: teléfono y foto de perfil, activo, datos de informe (contacto, cargo, ciudad, dirección, recinto). RUT sigue opcional, alineado con la matriz y con el criterio de “mínimo para iniciar”.

Pantallas

Todas las rutas de la hoja Pantallas existen, más: editar perfil, recuperar clave, y pantallas de informe embebidas en cliente/proyecto. El mapa de tabs usa /(main) en lugar de /(tabs) (detalle de implementación, no de producto).

Catálogos

Los valores cerrados de la hoja Catálogos coinciden con el código. Administración remota (RF-081) no está.

Reglas de negocio RN-01 a RN-15

Vigentes en validación y persistencia. Ajuste de producto: para iniciar un levantamiento solo son obligatorios cliente, proyecto y tipo de servicio. Alcance, estado, m² y sectores se exigen al cerrar (RN-05 a RN-07). Los campos del PDF se avisan con banner, no bloquean el inicio. Un finalizado se puede reabrir (extiende RN-04).

8. Brechas que sí bloquean “producción”

  • Build nativo de tienda: configurar EAS, applicationId / bundle identifier, iconos de store, cuentas Play/App Store y un binario firmado. Hoy solo corre en Expo Go / web.
  • QA en dispositivo real: cámara, permisos, offline de verdad, reconexión y PDF en Android e iOS. No hay suite de tests en el repo.
  • Migraciones aplicadas en el proyecto Supabase de producción: schema + hardening + teléfono/foto de perfil. Sin eso, Auth o sync fallan.
  • Política de backup y de usuarios: quién crea cuentas, qué pasa si se desactiva un técnico (activo existe), retención de fotos.

9. Brechas que no bloquean un piloto

  • Roles supervisor/admin y panel web (fuera de esta entrega).
  • Excel de sectores/elementos.
  • Magic link, push notifications, Sentry, cifrado en reposo, tenant multi-empresa.
  • Sequence SQL del correlativo (mitigado por unique; dos técnicos offline el mismo año podrían chocar y el segundo fallaría al sync).
  • SQLite en lugar de AsyncStorage.

10. Recomendación

Declarar el producto de terreno cerrado para piloto controlado (técnicos reales, proyecto Supabase de producción, cuentas creadas a mano, app vía Expo interno o APK interno cuando exista EAS).

No declarar listo para producción LANDES / tiendas hasta: (1) build EAS Android+iOS, (2) prueba de campo de un ciclo completo con fotos y PDF, (3) confirmar backups y migraciones en el proyecto de nube, (4) actualizar la matriz Excel para que deje de ser la fuente desfasada.

Siguiente entrega de producto, si se retoma el alcance original: visibilidad supervisor (RF-004 / RF-070 / SB-03), panel web (RF-080) y correlativo en SQL (SB-06).
